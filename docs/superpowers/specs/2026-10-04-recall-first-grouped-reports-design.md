# 미탐 우선 개선과 검증된 중복 보고서 통합 설계

- 작성일: 2026-10-04
- 기준: PR #213의 원본 보존형 후보 처리와 검증된 Finding 표시 묶기
- 상태: 설계 검토 대기

## 목적과 성공 기준

SASTSIMI의 Python 제품 코드 분석에서 미탐을 줄이는 것이 첫 번째 목표다. 두 번째 목표는 같은 취약점 경로에서 나온 제출용 보고서가 여러 개 보이는 문제를 줄이는 것이다. 사용자가 말한 “중복 제거”는 후보·Finding·PoC를 삭제하거나 조기 선별한다는 뜻이 아니다. 원본 결과와 직접 링크를 모두 보존하면서, 독립적으로 검증된 동일 근본 원인만 보고서 단계에서 하나로 제시한다.

두 목표를 서로 다른 지표로 검증한다. 정답이 코드와 재현으로 확인된 고정 커밋에서 취약점별 탐지 여부 및 누락 단계, 원본 Finding 수, 제출용 보고서 수, 잘못 합쳐진 서로 다른 경로 수, 토큰·시간을 변경 전후에 측정한다. “모든 저장소에서 미탐 0건”이나 “Finding이 있으면 제보 가능”을 성공 기준으로 주장하지 않는다.

## 현재 동작과 선택한 접근

현재 정적 결과의 원본과 정확한 후보 출처는 보존된다. Discovery의 `EXCLUDE`는 후속 심층 분석에서 빠지고 `UNDECIDED`는 진행한다. PR #213의 `finding_flow.py`, `finding_groups.py`, `finding_group_projection.py`는 검증된 동일 Python 입력→위험 동작 흐름만 읽기 시점에 묶는다. 대시보드 전체 ZIP에도 대표 보고서를 앞에 두고 다른 회원의 원본을 별도 경로에 담는 선택 정보가 있다. 그러나 `simple_runtime_composition.py`의 `report(finding_id)`와 `export_report_bundle(finding_id)`는 Finding별로 작동하며, 모든 회원의 사실·PoC·증거를 검증해 담은 제출용 그룹 묶음은 없다. 기존 오프라인 재생에서 일부 화면 그룹은 줄었지만 정적 후보 수는 변하지 않았고, 새 코드의 실분석 미탐 개선은 아직 입증되지 않았다.

후보를 CWE·파일·sink 이름만으로 초기에 합치면 비용은 줄 수 있으나 다른 입력과 분기를 지워 미탐 위험을 높인다. 자유 형식 LLM 중복 판정은 추가 비용과 거짓 병합 위험이 있다. 선택한 방식은 **후보 단계는 원본 보존, 최종 단계는 검증된 동일 흐름의 보수적 통합**이다. 증명이 부족한 Finding은 별도 보고서로 남으며, 자동 통합률을 높이기 위해 판정 기준을 완화하지 않는다.

## 범위와 데이터 흐름

1. 기존 Python 제품 파일 범위와 파일×규칙 커버리지 판단을 유지한다. 정적 검사 오류와 미지원 제품 파일은 후보 없음으로 바꾸지 않고 기존 `PARTIAL`/오류 계약에 남긴다. 원본 정적 결과, 후보 ID, 엔진 출처, Discovery 판정, 가설 및 PoC 체크포인트를 변경하지 않는다.
2. 고정 커밋의 정답 있는 소형 Python 저장소 두 종류와 기존 저장 결과를 이용해 각 정답의 `정적 후보 → Discovery → 가설 → 검증 → Finding → 보고서` 경로를 추적한다. 정답 설명은 분석 프롬프트·대상 체크아웃에 넣지 않는다. 정답 목록은 소스와 실행 근거를 사람이 재확인한 뒤 고정하며, 저장소 설명만으로 취약하다고 간주하지 않는다.
3. 먼저 실제 누락의 **최초 단계**를 확인한다. 그 단계에서 재현된 공통 원인만 최소 수정한다. 예를 들어 후보 미수집이면 탐지 규칙·Python 사실 추출을, 잘못된 `EXCLUDE`면 Discovery 근거·재검토 조건을, 검증 오류면 해당 상태 처리를 고친다. 원인이 밝혀지지 않은 상태에서 모든 호출을 늘리거나 광범위한 새 후보를 추가하지 않는다. 각 수정은 대상 저장소명·경로를 하드코딩하지 않고 독립 보류 저장소와 비용 지표로 회귀 검증한다.
4. Finding 생성·PoC·기술 게이트·Scope Gate는 현재 기준을 유지한다. `confirmed`는 실행된 PoC와 실제 근거가 있을 때만 가능하며, 전체 정적 커버리지나 제보 허가는 별도로 표시한다.
5. 최신 성공 체크포인트에서 읽기 전용 Finding 그룹을 계산한다. 동일 분석·워크스페이스·커밋·CWE와 고정 소스의 정확한 입력, sink callsite/인자, 경로 및 관련 분기가 같을 때만 자동 그룹화한다. 다른 입력→위험 동작 경로는 같은 제목이나 CWE라도 분리한다. 지원하지 않거나 모호한 흐름은 `GROUPING_UNDETERMINED` 단독 그룹으로 둔다.
6. 보고서가 모두 현재 유효한 `PROVEN_SAME_FLOW` 그룹에 한해 **제출용 그룹 묶음 하나**를 만든다. 기본 영문·국문 본문은 대표 Finding의 현재 안전 투영본을 사용하고, 그룹 ID와 포함된 Finding·검증 근거를 결정적으로 덧붙인다. 각 회원의 기존 `report_en.md`, `report_kr.md`, PoC, 증거, 개별 ZIP은 그대로 직접 조회할 수 있다. 그룹 묶음에는 `report_en.md`, `report_kr.md`, `evidence/group-manifest.json`, 회원별 검증된 PoC·증거를 구분된 경로에 넣는다. 보고서의 영향을 합성하거나 누락 필드를 LLM으로 만들어내지 않는다.

## 그룹 보고서의 안전 계약

- 그룹 생성은 모든 회원의 현재 `FINDING_DONE`, `TRUE` 최종 검증, 유효한 PoC, 통과한 기술 게이트, `REPORT_DONE`과 고정 소스 해시를 다시 확인한다. 한 회원이라도 폐기·오류·과거 버전이면 그룹 내보내기를 중단하고 기존 개별 보고서만 노출한다.
- 자동으로 하나의 제출용 본문을 만들려면 기존 번들의 구조화된 사실인 대상 커밋, CWE, 패키지, 영향·패치 버전, 심각도, Scope Gate 상태와 제보 허가가 충돌하지 않아야 한다. 필수 사실이 없거나 차이가 있으면 화면상 관련 그룹으로 보일 수 있어도 **제출용 그룹 묶음은 생성하지 않는다**. 자유 형식 영향 설명의 동등성을 추측하지 않고 대표 본문의 검증된 주장만 사용한다. 서로 다른 회원의 Scope Gate 결과 중 더 허용적인 값을 채택하지 않는다.
- 그룹 본문의 대표 선택은 안정적인 기존 F-NNN 순서로 한다. 대표 본문에 별도 Finding의 추가 주장이 필요한 경우 자동으로 문장을 합치지 않고 원본 보고서 링크와 증거 목록만 붙인다. 그룹 묶음은 사람이 제보 전에 검토할 초안이며 `UNCERTAIN`/`OUT_OF_SCOPE`를 자동 제보 가능으로 승격시키지 않는다.
- 기존 per-Finding 번들 검증, 파일 크기·경로·해시·민감정보 투영 검사를 재사용한다. 내보내기는 버전과 회원 해시로 식별하고 원자적으로 기록한다. 최신 체크포인트와 맞지 않는 캐시 파일은 재사용하지 않는다. 읽기/내보내기 오류는 해당 그룹 실패로 명시하고 원본 Finding이나 분석 상태를 덮어쓰지 않는다.
- 기존 그룹 ID와 원본 F-NNN 링크는 유지한다. 내보내기 캐시는 그룹 ID와 회원 번들의 내용 해시로 구분한다. 기존 DB 스키마와 완료 체크포인트를 마이그레이션하지 않는다. 재개 후 같은 유효 증거에는 같은 그룹과 보고서 수가 나오며, 오래된 분석은 증명이 부족하면 단독 항목으로 남는다.

## CLI·대시보드 계약

`finding_count`는 언제나 원본 Finding 수다. 별도로 검증된 그룹 수, 실제 제출용 그룹 묶음 수, 통합 불가·판정 불명 그룹 수를 표시한다. 기본 보고서 목록은 제출용 그룹 묶음 하나를 대표 카드로 보여주되, 모든 회원의 F-NNN·개별 보고서·PoC·증거로 바로 이동할 수 있다. 그룹 묶음이 없는 회원은 기존 개별 보고서를 보여준다. 예전 API 응답과 기존 `report F-NNN`/ZIP 링크는 계속 동작한다. 화면의 그룹 수나 `confirmed` Finding 수를 전체 분석 `COMPLETE` 또는 외부 제보 허가의 동의어로 사용하지 않는다.

## 검증과 판정 기준

- 손으로 확인한 두 취약 Python 저장소와 다른 구조의 보류 저장소를 고정 커밋·동일 모델·동일 설정으로 평가한다. 변경 전후 정답별 `탐지/미탐/미확정`, 최초 누락 단계, 후보→가설→검증 전환율, 원본 Finding과 제출용 보고서 수, 토큰·실행시간을 기록한다. 실행을 끝내지 못한 항목은 미탐이나 성공으로 세지 않는다.
- 같은 흐름을 다른 엔진·가설이 보고한 양성 사례는 그룹 보고서 하나로, 같은 sink지만 다른 요청 키·분기·callsite·영향을 가진 음성 사례는 별도 보고서로 남는 회귀 테스트를 둔다. 병합으로 사라진 서로 다른 검증 경로는 허용하지 않는다. 실제 중복 감소량이 없으면 그 사실을 기록하고 모호한 병합으로 수치를 맞추지 않는다.
- 비용은 단계별 LLM 호출·입출력 토큰·실행시간으로 측정한다. 미탐 개선으로 비용이 증가하면 새로 찾은 유효 취약점당 비용을 함께 제시하며, 저장소별 하드코딩이나 무제한 후보 확장으로 수치만 높이지 않는다.
- 오래된 분석 재개, 중간 종료 후 재개, 잘못된 PoC/오래된 보고서, 고정 소스 변경, 파일 경로 우회, 서로 다른 Scope Gate, 그룹 묶음 생성 실패, 기존 직접 링크와 다운로드, 미검증 제품 파일의 `PARTIAL` 유지를 테스트한다. 전체 회귀·정적 타입/린트 검사와 실제 소형 저장소 실행 결과를 기록한 후에만 PR의 기능 완료를 주장한다.

## 제외 범위와 후속 결정

원본 후보 삭제, 초기 가설 수 제한, 자유 형식 LLM 중복 투표, 기존 Finding/PoC 재분류, 자동 외부 제보, 모든 저장소의 취약점 완전 탐지 보장은 이 설계의 범위가 아니다. 누락 원인의 실제 계측 전에 특정 정적 규칙이나 프롬프트 변경을 약속하지 않는다. 계측으로 확인한 첫 번째 범용 누락 원인을 수정하고 다시 측정한다. 추가로 독립적인 누락 원인이 드러나면 그 원인과 필요한 후속 변경을 별도 범위로 보고한다.
