# 협업 Issue 구조와 쉬운 문서 체계 설계

## 1. 목적

이 설계는 Architecture v5 검토 작업을 다음 두 가지 방향으로 정리한다.

1. PM이 전체 목표를 관리하는 상위 Issue를 유지하고, 각 역할 담당자가 자신의 세부 작업을 하위 Issue로 직접 만들어 수행한다.
2. 처음 참여한 팀원도 README와 업무 지시 문서를 한 번 읽고 무엇을 해야 하는지 이해할 수 있도록 전문용어를 줄이고 쉬운 설명을 붙인다.

현재 저장소는 설계 검토 단계다. 이 변경은 Architecture v5를 승인하거나 구현 완료로 바꾸지 않는다. 현재 상태인 `DESIGN_AUTHORED / REVIEW_REQUIRED / NOT_IMPLEMENTED`를 유지한다.

## 2. 현재 문제

현재 문서에는 PM이 Parent Epic #1에서 전체 검토를 관리하고, 역할별 Issue #2–#9에서 담당자가 작업한다는 흐름은 있다. 그러나 담당자가 자기 역할의 세부 작업을 하위 Issue로 직접 나누고 관리해야 한다는 규칙은 명확하지 않다.

또한 README, 협업 문서와 governance 문서에 `candidate baseline`, `contract`, `runtime validator`, `upstream`, `downstream`, `artifact`, `human handoff`처럼 처음 참여한 팀원이 바로 이해하기 어려운 용어가 많다. 일부 용어는 데이터 형식과 상태값을 정확히 맞추기 위해 유지해야 하지만, 현재는 쉬운 설명 없이 사용되는 경우가 많다.

마지막으로 저장소에 문서가 많지만 각 파일이 무엇을 설명하고 누가 읽어야 하는지 한곳에서 확인하기 어렵다.

## 3. Issue 계층

기존 Issue는 삭제하거나 다시 만들지 않는다. 기존 링크와 검토 기록을 보존하기 위해 다음 구조로 사용한다.

```text
#1 PM 전체 관리 Issue
├─ #2 LLM 탐색·체이닝 역할별 상위 Issue
│  ├─ 담당자가 만드는 세부 하위 Issue
│  └─ 담당자가 만드는 세부 하위 Issue
├─ #3 정적분석·컨텍스트 역할별 상위 Issue
│  └─ 담당자가 만드는 세부 하위 Issue
├─ #4 단독 구현·통합 개발 역할별 상위 Issue
├─ #5 PM·아키텍처·워크플로 역할별 상위 Issue
├─ #6 Gate·Finding·보고서 역할별 상위 Issue
├─ #7 검증·반박·플레이북 역할별 상위 Issue
├─ #8 동적검증·Sandbox 역할별 상위 Issue
├─ #9 데이터·평가·예산 역할별 상위 Issue
└─ #10 전체 최종 검토 Issue
```

### 3.1 PM의 책임

PM·아키텍처 담당자는 다음을 수행한다.

- #1에 전체 목표, 역할별 진행 상태와 최종 검토 조건을 유지한다.
- 역할 사이에서 같은 데이터나 상태를 다르게 이해하는 문제가 생기면 조정한다.
- 하위 Issue를 대신 세세하게 작성하지 않는다.
- 담당자가 만든 하위 Issue가 상위 역할 Issue와 연결됐는지 확인한다.
- 모든 역할별 상위 Issue가 끝난 뒤 #10의 전체 검토를 시작한다.
- 설계 승인 상태는 별도의 최종 승인 PR에서만 변경한다.

### 3.2 역할 담당자의 책임

각 역할 담당자는 다음을 수행한다.

1. 자신의 역할별 상위 Issue를 읽고 작업을 나눈다.
2. 한 번에 검토하고 완료 여부를 판단할 수 있는 크기로 하위 Issue를 직접 만든다.
3. GitHub의 하위 Issue 관계를 사용해 역할별 상위 Issue에 연결한다. 해당 기능을 사용할 수 없으면 본문에 `상위 Issue: #번호`를 적고 상위 Issue 체크리스트에도 링크한다.
4. 하위 Issue마다 목적, 할 일, 수정할 문서, 완료 조건과 필요한 검토자를 적는다.
5. 변경 PR에 `Closes #하위-Issue`와 `Refs #역할별-상위-Issue`를 함께 적는다.
6. 모든 하위 Issue와 관련 PR이 끝난 뒤 역할별 상위 Issue를 닫는다.

기존 #2–#9의 최초 생성자가 PM이더라도 앞으로의 세부 작업 분해, 본문 보완, 진행 상태와 완료 판단은 해당 역할 담당자가 맡는다.

### 3.3 하위 Issue 작성 형식

하위 Issue 제목은 `[R번호-순번] 구체적인 작업` 형식을 권장한다. 예시는 `[R2-01] AST 결과의 코드 위치 표시 방법 확정`이다.

본문에는 다음 항목을 사용한다.

```markdown
## 한 줄로 설명하면
이 작업이 무엇인지 쉬운 문장으로 적습니다.

## 왜 필요한가
지금 어떤 문제가 있고 왜 해결해야 하는지 적습니다.

## 이번에 할 일
- 실제로 확인하거나 수정할 일을 적습니다.

## 수정하거나 확인할 문서
- `정확한/파일/경로.md`

## 완료 조건
- [ ] 결과를 보고 완료 여부를 판단할 수 있는 조건을 적습니다.

## 연결
- 상위 Issue: #역할별-상위-Issue
- 관련 역할: 검토가 필요한 다른 담당 영역
```

## 5. 쉬운 문서 작성 원칙

### 5.1 기본 원칙

- 한국어와 짧은 문장을 우선한다.
- 한 문장에는 가능한 한 한 가지 내용만 담는다.
- 표 제목과 문서 제목은 처음 참여한 팀원이 이해할 수 있는 표현을 먼저 사용한다.
- 영어 전문용어가 꼭 필요하면 처음 나올 때 `영문 용어(쉬운 한국어 설명)` 형식으로 설명한다.
- 같은 용어에는 문서마다 같은 쉬운 설명을 사용한다.
- 구현에서 정확히 일치해야 하는 데이터 이름, 필드명, 상태값은 바꾸지 않는다.
- 코드 블록, 데이터 형식과 Mermaid 노드의 식별자는 의미가 바뀌지 않도록 유지한다.
- 긴 상세 계약보다 먼저 ‘무엇을 위한 내용인지’를 설명한다.

### 5.2 공통 용어 예시

| 기존 표현 | 문서에서 사용할 표현 |
|---|---|
| candidate baseline | 검토 중인 설계 초안(`candidate baseline`) |
| contract | 입출력 약속(`contract`) |
| CodeWorkspace | AST와 SAST가 읽는 실행별 로컬 코드 폴더(`workspace_id`와 `commit_id`로 구분) |
| artifact | 도구가 만든 결과 파일이나 기록(`artifact`) |
| record | 정해진 형식의 데이터 묶음(`record`) |
| runtime validator | 프로그램 내부 규칙 검사기(`runtime validator`) |
| upstream / downstream | 앞 단계 / 뒤 단계(`upstream / downstream`) |
| owner | 담당자(`owner`) |
| reviewer | 검토자(`reviewer`) |
| Finding | 검토 대상으로 정리된 취약점 결과(`Finding`) |
| Gate | 다음 단계로 보내도 되는지 확인하는 검토 단계(`Gate`) |
| human handoff | 사람이 검토할 자료 전달(`human handoff`) |
| provenance | 가져온 출처와 변경 이력(`provenance`) |
| corpus | 반복 평가에 사용하는 예제 모음(`corpus`) |
| observability | 실행 상태와 오류를 확인할 수 있는 기록(`observability`) |

세부 설명은 새 `docs/GLOSSARY.md`에서 한곳에 관리한다.

### 5.3 문서 상단 안내

Architecture v5 번호 문서와 주요 Wiki 문서 상단에는 다음 안내를 둔다.

- **이 문서는 무엇을 설명하나요?**
- **누가 읽어야 하나요?**
- **읽은 뒤 무엇을 확인하거나 결정하나요?**

이 안내는 상세 기술 내용을 없애지 않고 독자가 필요한 문서인지 먼저 판단하도록 돕는다.

## 6. 문서별 수정 범위

### 6.1 저장소 첫 화면과 협업 안내

- `README.md`: 프로젝트 한 줄 설명, 현재 단계, 전체 흐름, 팀 역할과 Issue 운영 방식을 쉬운 순서로 재구성한다.
- `CONTRIBUTING.md`: PM 상위 Issue → 역할별 상위 Issue → 담당자 생성 하위 Issue → PR → 최종 검토 순서를 명시한다. 하위 Issue 작성 형식과 쉬운 용어 규칙을 포함한다.
- `docs/README.md`: 문서 정본, 참고 문서와 업무 문서의 차이를 쉽게 설명하고 전체 문서 지도로 연결한다.

### 6.2 협업·승인 규칙 문서

- `docs/governance/OWNERSHIP.md`: 영문 중심 역할 표현을 쉬운 한국어로 바꾸고, 역할 담당자의 하위 Issue 생성 책임을 추가한다.
- `docs/governance/OPEN_QUESTIONS.md`: 이미 확정된 역할 배정과 아직 필요한 GitHub 접근 권한을 분리한다. 각 미결정 사항을 쉬운 질문과 영향으로 표현한다.
- `docs/governance/REVIEW_CHECKLIST.md`: 하위 Issue 생성·연결·완료 조건 확인 항목을 추가하고 전문용어에 짧은 설명을 붙인다.

### 6.3 검토 업무 문서

- `docs/review/ISSUE_TRACKER.md`: #1, #2–#9, 담당자 생성 하위 Issue, #10의 관계를 표와 작업 순서로 설명한다.
- `docs/review/ISSUE_CATALOG.md`: 기존 상세 기준을 보존하면서 각 역할별 상위 Issue가 하위 Issue를 어떻게 나눠야 하는지 예시를 추가한다.
- `docs/review/FINDINGS.md`: 어려운 발견사항에 쉬운 요약 열을 추가하거나 첫 문장을 풀어 쓴다.
- `docs/review/PROVENANCE.md`: 해시와 출처 값은 그대로 두고 문서 목적과 주의사항을 쉬운 말로 보강한다.
- `docs/review/decisions/README.md`: 설계 결정을 언제, 누가, 어떻게 기록하는지 쉬운 절차로 바꾼다.

### 6.4 Architecture v5 기준 문서

- `docs/architecture-v5/README.md`: 영어 중심 설명을 줄이고 23단계에 쉬운 보충 설명을 붙인다.
- `01`–`13` 번호 문서: 문서 상단 안내, 공통 용어의 첫 사용 설명, 어려운 제목과 표 머리글을 정리한다.
- 데이터 형식과 상태값을 정의하는 `08-lightweight-data-contracts.md`는 정확한 이름을 유지하고 각 데이터 묶음 앞에 한 줄 설명을 추가한다.
- `13-architecture-diagrams.md`와 Wiki 다이어그램의 Mermaid 본문은 서로 같게 유지한다. 다이어그램 앞에 읽는 법을 추가한다.

### 6.5 Wiki와 보조 파일

- Wiki 문서는 번호 문서의 쉬운 요약이라는 성격을 더 분명히 한다.
- `_Sidebar.md`는 쉬운 한국어 제목을 사용한다.
- `index.html`, `theme.css`, `serve.ps1`은 실행 보조 파일이므로 코드 의미는 바꾸지 않고 문서 지도에서 용도만 설명한다.

### 6.6 새 문서

- `docs/GLOSSARY.md`: 프로젝트 전체 공통 용어의 쉬운 설명과 정확한 기술 이름을 함께 제공한다.
- `docs/DOCUMENT_GUIDE.md`: 저장소의 모든 문서와 Wiki 보조 파일을 하나씩 나열하고, 각 파일의 목적·권장 독자·기준 문서 여부를 설명한다.

`docs/superpowers/specs/`와 `docs/superpowers/plans/`는 설계 변경 작업의 기록이며 Architecture v5 내용의 기준 문서가 아니라는 점도 문서 지도에 표시한다.

## 7. GitHub Issue와 PR 반영

- #1에 Issue 계층과 담당자 하위 Issue 생성 규칙을 추가한다.
- #2–#9에 ‘담당자가 해야 할 첫 작업’으로 세부 하위 Issue 분해와 연결을 추가한다.
- #10에 모든 역할별 상위 Issue와 그 하위 Issue가 완료됐는지 확인하는 항목을 추가한다.
- Draft PR #11 본문에 새 협업 구조, 쉬운 문서 기준, 새 문서 지도를 반영한다.
- 기존 Issue 제목과 번호는 유지해 링크와 검토 기록을 보존한다.

## 8. 검증 기준

수정 후 다음을 확인한다.

1. README와 CONTRIBUTING만 읽어도 Issue 계층과 자신의 첫 작업을 설명할 수 있다.
2. #1은 PM 전체 관리 Issue, #2–#9는 역할별 상위 Issue, #10은 최종 검토 Issue로 일관된다.
3. 모든 역할별 상위 Issue에 담당자가 하위 Issue를 직접 만든다는 문구가 있다.
4. 모든 주요 문서가 `docs/DOCUMENT_GUIDE.md`에 한 번 이상 나온다.
5. 공통 전문용어는 `docs/GLOSSARY.md`에 쉬운 설명이 있다.
6. 데이터 이름과 상태값은 기존 정확한 표기를 유지한다.
7. 로컬 Markdown 링크 오류, 닫히지 않은 코드 블록과 뒤쪽 공백이 없다.
8. 정본과 Wiki Mermaid는 각각 8개이며 내용이 같다.
9. 설계 상태는 계속 `DESIGN_AUTHORED / REVIEW_REQUIRED / NOT_IMPLEMENTED`다.
10. Gate, Verification, Reporter와 사람의 권한 경계가 약해지지 않는다.

## 9. 완료 결과

작업이 끝나면 처음 참여한 팀원은 다음 순서로 업무를 시작할 수 있다.

1. README에서 프로젝트와 자기 역할을 확인한다.
2. CONTRIBUTING에서 Issue와 PR 작성 순서를 확인한다.
3. #1에서 자기 역할별 상위 Issue를 찾는다.
4. 역할별 상위 Issue를 읽고 세부 하위 Issue를 직접 만든다.
5. 문서 지도에서 수정할 파일의 목적을 확인한다.
6. 용어집에서 모르는 단어를 확인한다.
7. 하위 Issue 단위로 문서를 검토하고 PR을 만든다.
8. 역할별 작업과 최종 전체 검토를 거쳐 별도 승인 PR로 넘어간다.
