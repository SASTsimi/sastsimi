# 전체 현행 문서 가독성 정리 설계

작성일: 2026-10-16

대상 기준: 최신 `main`에서 분기한 `codex/docs-comprehensive-readability`

보관 위치: 저장소의 현행 문서 검증 규칙이 허용하는 `docs/plans/`

## 1. 목적과 비목표

README에서 연결되는 몇 페이지만 보기 좋게 만드는 데 그치지 않고, 사용자가 현재 동작을 이해하고 실행·복구·검증하는 데 쓰는 문서 전체를 일관된 구조로 정리한다. 필요한 명령, 제한사항, 안전 경계와 검증 근거는 보존한다. 문서 정리가 분석 파이프라인의 동작이나 판단을 바꾸지는 않는다.

이번 작업은 새로운 기능 구현, 과거 실험 결과 재해석, 취약점 검증 기준 완화, 프롬프트 변경을 포함하지 않는다. 원본을 없애서 문서 수를 줄이는 작업도 아니다.

## 2. 조사 결과와 범위

현재 저장소에는 추적되는 Markdown 문서 138개가 있다. 이 중 Agent 실행에 사용되는 프롬프트 템플릿 25개와 과거 설계·계획·검증 기록은 동작·감사 원본이므로 본문을 보존한다. 나머지는 용도에 따라 다음과 같이 다룬다.

| 문서군 | 이번 작업 |
| --- | --- |
| `README.md`, `CONTRIBUTING.md`, 현재 운영 안내, 용어집, 문서 지도 | 이용 순서에 맞게 본문을 정리하고 중복을 줄인다. |
| `docs/architecture/`의 현재 구조 설명, `docs/dashboard-read-model.md`, 현재 제약 안내 | 주제별 소제목·요약·경계와 관련 문서 링크를 정리한다. 긴 문서는 필요 시 분리한다. |
| `docs/decisions/ADR-*.md`의 채택된 결정 | 결론과 이유를 바꾸지 않고 찾기 쉬운 색인·짧은 길잡이를 추가한다. |
| 과거 설계·계획·검증 기록 | 본문과 수치·날짜를 유지하고, 별도 색인에서 작성 시점과 현재 참고 위치를 설명한다. |
| `src/sastsimi/prompts/templates/` | 원본 문구·스키마를 수정하지 않는다. |

위 분류는 파일명만으로 자동 결정하지 않는다. 각 파일의 실제 목적과 코드·테스트의 참조를 확인한 뒤 현행 설명과 기록 원본을 구분한다. 특히 오래된 설계가 현재 아키텍처처럼 보이지 않게 표시한다.

## 3. 정보 구조

채택한 방식은 **주제별 분리 + 기존 페이지의 길잡이 유지**다. 제목만 줄이는 방식은 긴 문제 해결·증거 문서의 탐색 문제를 남기고, 138개 Markdown 전체를 재작성하는 방식은 원본 프롬프트·실험 기록을 훼손할 위험이 크다.

최상단 `README.md`는 소개·빠른 시작·결과 해석·검사 범위·문서 진입점에 집중한다. `docs/README.md`와 `docs/DOCUMENT_GUIDE.md`는 같은 목록을 반복하지 않고, 사용자 작업별 진입과 전체 문서군의 현재/기록 구분을 각각 맡는다. 설치, Provider, 분석·재개, 대시보드, 보고서, 문제 해결, 구현 구조, 평가 방법 문서는 각 문서의 첫 화면에서 **대상 독자·핵심 경로·주의할 상태**를 파악할 수 있게 한다.

긴 문서의 세부 주제는 실제 필요가 확인되면 별도 페이지로 이동한다. 예를 들어 671줄의 문제 해결 문서는 증상별 진단을 짧게 보여 주고, 길고 전문적인 PoC 환경·과거 실패 재개 절차를 독립 페이지로 나눌 수 있다. 분석 사용법, 온보딩 증거, 런타임 복구, Python 탐지율 평가도 같은 기준으로 검토한다. 원래 URL의 문서는 삭제하지 않고 짧은 설명과 새 본문 링크가 있는 길잡이로 남긴다.

과거 계획·설계·검증 기록은 파일명에 날짜가 있든 없든 본문을 확인해 `docs/plans/README.md`, `docs/validation/README.md` 같은 색인에서 찾을 수 있게 한다. 각 기록의 미완료 체크박스를 현재 작업 지시로 오인하지 않도록 색인에서 작성 시점(알 수 있을 때)과 보존 목적을 설명한다. 채택 ADR 13개와 `docs/decisions/`에 함께 놓인 날짜 기반 과거 설계 3개는 구분한다. 현재 문서 지도의 잘못된 ADR 개수도 실제 목록에 맞춘다.

## 4. 본문 보존과 삭제 기준

각 현행 문서에서 먼저 명령어·상태값·오류 코드·정책/안전 제한·계측 수치·구현 근거를 표로 대조한다. 삭제할 수 있는 것은 같은 최신 설명이 새 위치에 남고 사용자나 검증자가 잃는 정보가 없는 중복 문장·오래된 안내뿐이다. 모순되거나 낡은 설명은 코드, CLI 도움말, 테스트, 최근 승인된 결정과 대조해 교정하고, 출처가 불명확하면 지우거나 현재 사실로 단정하지 않는다. 변경 이유를 PR에 기록한다.

다음 의미는 표현을 간결하게 바꾸더라도 유지한다.

- `COMPLETE`, `PARTIAL`, `BLOCKED`, `INCONCLUSIVE`, `HOLD`와 진행률의 구별. 100% 진행률은 취약점 확정이나 완전한 검사 범위를 뜻하지 않는다.
- Python 제품 코드 범위, 정적 검사 미검증 조합, 제외 범위와 재개 조건. 미검증을 탐지 없음으로 바꾸지 않는다.
- PoC·Scope Gate·보고서의 독립 검증 조건. 제보 가능 여부를 자동으로 보장하지 않는다.
- 인증 토큰, 프롬프트, 저장소 코드·로컬 경로의 비노출 경계와 Provider별 추가 사용량 안내.
- 날짜가 붙은 측정 수치의 대상 커밋·조건·한계. 후속 검증과 섞어 최신 성능값처럼 보이지 않게 한다.

기존 문서의 일회성 측정값이나 오래된 설계는 현재 흐름 설명에서 분리하되 원래 기록을 보존하고 링크한다. 예를 들어 예전 보고서 그룹 수치와 후속 재검증의 0건 결과를 같은 현재 성능처럼 병기하지 않는다.

## 5. 링크·앵커·명령 호환성

외부에서 이미 연결한 경로와 명시적 앵커를 보존한다. `README.md`의 빠른 시작·분석 흐름·결과 해석·검사 범위, `docs/usage.md`의 `analyze`/`resume`/`dashboard`/`results`/`runtime`, Provider별 제목, 문제 해결의 Docker·PoC 제목 및 증상 링크가 주요 호환성 지점이다. 섹션을 이동하면 원래 위치에 목적과 새 링크를 둔다.

기존 상대 Markdown 링크, 프래그먼트 링크, 코드 블록 밖의 평문·백틱 경로, 계획 문서의 `**Spec:**` 경로를 검색한다. 현재 문서 링크 검증기는 파일 존재와 일부 구조만 확인하고 제목 프래그먼트·평문 경로는 보지 않으므로, 검증 범위를 보강하거나 별도 검증을 추가한다. 프래그먼트 검사는 코드 예시를 제외하고 GitHub의 자동 제목 앵커(한글·중복 제목 포함)와 명시적 HTML 앵커를 구분한다. 새 색인은 순환 링크를 피하고 현재 정보와 보존 기록의 차이를 명시한다.

PowerShell 예시는 실제 CLI 옵션과 대조한다. Windows `.venv` 설치, Codex 로그인, `sastsimi setup`, 정확한 커밋 지정 분석, 상태·재개, 대시보드, Finding 보고서 명령은 복사 가능한 형태로 유지한다. Linux/WSL 예시는 별도 표기한다. 문서 검증 과정에서 로그인·새 분석은 실행하지 않고 CLI `--help`, 구현 코드와 계약 테스트로 구문을 확인한다. 기존 문서 계약 테스트가 요구하는 명령·문구를 단순히 제거하지 않으며, 계약이 낡은 경우는 구현 근거와 함께 테스트를 갱신한다.

## 6. 구현 순서

1. 모든 추적 Markdown을 현행 안내·채택 결정·과거 기록·실행 프롬프트로 분류하고, 현재 문서의 링크·앵커·명령·중복·모순 목록을 확정한다.
2. README와 문서 지도에 작업별 읽기 순서와 현재/기록 경계를 먼저 만든다. 대시보드 읽기 모델 등 빠진 현행 안내를 편입한다.
3. 설치·Provider·사용법·문제 해결·온보딩·아키텍처·평가 안내를 주제별로 정리한다. 길고 전문적인 내용만 하위 문서로 옮기고 원래 경로는 길잡이로 남긴다.
4. 보존 원본을 수정하지 않고 계획·검증·결정 색인을 정리한다. 기록에서 현재 참고 문서로 돌아오는 경로를 제공한다.
5. 링크·앵커·평문 경로·명령 검증과 문서 계약 테스트를 보강한 뒤 전부 실행한다. PR에서 변경·이동·삭제 이유를 파일별로 요약한다.

독립된 문서군은 병렬 편집할 수 있지만 README·지도·검증 스크립트는 마지막에 통합해 충돌과 중복을 점검한다.

## 7. 검증과 완료 기준

- `scripts/validate-current-docs.ps1`가 통과하고, 모든 추적 Markdown의 로컬 링크·사용 중인 프래그먼트·이동된 경로를 검사한다.
- 문서 계약 테스트(`tests/contract/test_current_documentation.py`, `test_operator_docs.py`, `test_distribution.py`)와 관련 테스트가 통과한다. 명령 예시는 현재 CLI와 대조한다.
- 25개 실행 프롬프트, 채택 ADR의 결정·상태, 날짜 기반 실험의 원본 수치·판정은 변경되지 않는다. 필요한 본문 이동은 정보 누락이 없는지 대조한다.
- 대표 사용 경로(처음 설치, Provider 선택, 분석·재개, 대시보드, 결과/보고서, 대표 오류 복구)를 링크를 따라 직접 읽어 문서 사이의 단절·중복·오해를 확인한다.
- 검증이 통과하면 새 브랜치의 PR로 내고 CI를 확인한 다음 병합한다. CI 실패나 링크 파손이 남으면 완료로 보고하지 않는다.

## 8. 위험과 완화

문서 제목 변경은 GitHub 자동 앵커를 깨뜨릴 수 있다. 제목 유지 또는 명시적 호환 앵커·원위치 링크로 막는다. 오래된 설계를 최신 설명으로 옮기면 의미가 달라질 수 있으므로 원본은 보존하고 현행 문서에서 시점을 구분한다. 테스트 문자열을 맞추려 부정확한 설명을 남기는 대신 실제 코드 계약을 확인한 뒤 문서와 테스트를 함께 고친다. 양이 많아도 한 번에 삭제하지 않고 분류→이동→검증의 순서로 변경한다.
