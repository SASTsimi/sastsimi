# Product-code static-analysis scope

## Purpose and boundary

The static-analysis scope is tracked, deployable product source, not test-only source. The same effective scope must govern AST, OpenGrep, Semgrep fallback, CodeQL, file–rule coverage, and the source list subsequently shown to analysis agents. Test-only files are dropped before scanning and do not count as successful scans or unresolved product-code scans. There is no `EXCLUDED_TEST_FILE` record, per-file exclusion report, or test-inclusion option; this is the user's explicit simplification after approving the first design.

This is a scope change, not a claim that all remaining product code will scan successfully. Parser errors, timeouts, CodeQL scope mismatches, or unknown product-code coverage still block `COMPLETE`. The previously cancelled request to add new CodeQL languages is not part of this design: CodeQL's existing language scope remains unchanged.

## Selected approach

Use one deterministic, versioned `StaticFileScope` built from the pinned commit's NUL-delimited `git ls-files` result. It exposes only selected product paths, a fingerprint, and the policy version; the classifier discards test-only candidates internally without retaining an exclusion list or reason. The full tracked list exists only in the bootstrap integrity check, outside `StaticFileScope`. Classifier policy version 3 uses exact path components `test`, `tests`, `__test__`, `__tests__`, `spec`, `specs`, `__specs__`, `e2e`, `testdata`, `unit_tests`, `integration_tests`, and `functional_tests`, plus anchored language-specific test basenames including MTS/CTS. Substring matching (`contest`, `testimonials`) is forbidden. Ambiguous names outside a clear test directory remain in product scope unless bounded head/tail content sampling finds high-confidence test evidence, including in files larger than the sample window. Generic `fixtures`, `mocks`, `examples`, and `integration` directories are not excluded by name alone. A source path referenced as a verified declared product entry point remains selected, including relative paths without `./` and wildcard export targets matched against tracked files. Package manifests are read in full up to a finite 4 MiB limit; test-only manifests are ignored as declarations, while an unreadable product manifest that might deploy a test-like path fails closed with `STATIC_SCOPE_MANIFEST_UNVERIFIED` instead of silently discarding product code. No Dify-specific path appears in the classifier.

The alternative of independently configured ignore globs for each engine is rejected because the scanners and coverage denominator could diverge. CodeQL receives a temporary selected-source tree so files dropped by the common scope cannot enter extraction. This changes extraction context, so a real fixture must prove the file set and failure must remain visible rather than assuming input parity.

## Data flow and engine parity

The manifest is created before repository profiling or scanning. AST receives its selected Python paths; OpenGrep's initial scan and bounded retries receive explicit selected paths instead of the repository root; Semgrep fallback receives the same unresolved selected file–rule pairs. Existing language-to-rule mapping still determines which pairs are applicable. Agent source surveys use selected paths while an independent complete tracked-file manifest remains available for integrity checks.

CodeQL must receive only selected product source while creating its database, not merely discard findings afterward. Stage the selected paths in an isolated input directory for both SimpleRuntime and production CodeQL provisioning, then verify a real product/test fixture against the installed CodeQL 2.27.0. If an alternative CodeQL configuration filter is used, its exact input parity must first be demonstrated with the same fixture; the existence of a CLI flag is not sufficient proof. If input parity cannot be proven for a repository or CodeQL build, return a scope/coverage failure and do not mark the analysis complete. Reusing a pre-exclusion database is forbidden.

`StaticFileScope` is also the single input to expected file–rule pairs. Test-only paths are outside the denominator, never added to verified pairs. Coverage policy version 2 treats every selected file whose extension matches no rule language and is outside an explicit non-source extension/basename allowlist as an unsupported candidate, including previously unknown source extensions. Such candidates block `STATIC_DONE`; the allowlist may need generic validation for unusual repositories and is not a Dify-specific escape hatch. Coverage evidence and reports retain the product-scope policy version, selected source count, per-engine attempted/verified/unresolved product pairs, and remaining product-code errors, but no excluded-file count or list. If scanner output unexpectedly refers to a dropped path or a selected path is omitted from the asserted scan result, fail closed rather than silently accepting the mismatch.

## Persistence, configuration, and resume

No new setup or profile option is added. Record the product-scope policy version in the analysis/checkpoint and include the selected-path manifest digest in coverage, OpenGrep batch, and CodeQL database cache identities. A resume from the old full-repository scope must not reuse previous scan proofs or downstream findings as if they had the same denominator. The safe operator path is a new analysis identity for the product scope; an old in-flight identity keeps its historical scope or stops with an explicit scope-change error. Existing artifacts remain intact and labeled with their original scope.

## Validation and Dify retest

Unit tests cover exact directory and filename patterns, ambiguous product filenames, declared product entry points, mixed-language paths, no public test-inclusion option, and deterministic policy hashes. Integration tests assert identical engine input sets, CodeQL fixture extraction, cache separation, fail-closed scope mismatch, resume behavior, no persisted per-file exclusion records, and preservation of product-code gaps. Existing static and provider regression suites run with expectations updated for the new default scanner input.

For Dify commit `8387590ace4a094de812b7847fc6a4c3a27cd52b`, compare the selected product paths against project entry points and representative backend/frontend files before accepting the new scope. Restart the Dify trial under the new scope identity, reuse only scope-compatible evidence, measure remaining parser errors/timeouts among product paths, and continue through agents/PoC/reports only if all required product coverage is verified. Record actual outcomes without manufacturing `COMPLETE` or `confirmed`.

## Sources and limitations

The CodeQL CLI documents database creation and optional code-scanning configuration: <https://docs.github.com/en/code-security/reference/code-scanning/codeql/codeql-cli-manual/database-create>. Neither documentation nor post-filtered findings prove which files were extracted; the selected-source fixture must establish that locally. No pathname-only policy can prove the deployability of every unusual repository file, so uncertain candidates remain included. Operators see the product-scope policy and unresolved product-code errors, not individual dropped test paths.
